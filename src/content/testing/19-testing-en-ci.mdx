## Concepto

**Qué problema resuelve.** Las pruebas sirven si corren siempre, no cuando alguien se acuerda. La CI las corre en cada PR, y si fallan, no se mergea.

**Un pipeline típico, de rápido a lento:**

1. Instalar dependencias (`npm ci`).
2. Lint y tipos.
3. Tests unitarios (`npm test`).
4. Build (`npm run build`).
5. E2E (`npx playwright test`), con el navegador instalado.
6. Si algo falla: guardar el reporte y las trazas como artefactos.

## Ejemplo

Un workflow de GitHub Actions para Rollito (de referencia; verificá las versiones vigentes de cada `action` antes de usarlo):

```yaml
name: CI
on: [pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npm ci
      - run: npm test
      - run: npx playwright install --with-deps chromium
      - run: npm run test:e2e
      - if: failure()
        uses: actions/upload-artifact@v4
        with:
          name: reporte-playwright
          path: playwright-report/
```

Hoy Rollito corre estas pruebas a mano antes de cada push (y Render vuelve a construir el sitio); con este workflow pasarían a correr solas en cada PR.
