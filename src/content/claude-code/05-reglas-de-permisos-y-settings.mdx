## Concepto

**Qué problema resuelve.** Aprobar `npm test` veinte veces por día cansa; dejar que Claude lea tu `.env`, no debería pasar nunca. Las reglas de permisos dejan eso configurado una vez.

**Dónde se configura** (de mayor a menor prioridad):

1. Configuración administrada por la organización.
2. `--settings` al abrir.
3. `.claude/settings.local.json`: personal, de este proyecto.
4. `.claude/settings.json`: del proyecto, se commitea.
5. `~/.claude/settings.json`: personal, para todos tus proyectos.

Las listas como `permissions.allow` **se suman** entre archivos; no se reemplazan.

**Las reglas:** `Herramienta` o `Herramienta(especificador)`. Se evalúan en orden **deny → ask → allow**, y gana la primera que coincide.

**Comandos útiles:** `/permissions` (reglas activas y de dónde vienen), `/config` (opciones comunes), `/status` (qué archivos de configuración se cargaron).

## Ejemplo

Un `.claude/settings.json` de proyecto (ejemplo basado en la documentación):

```json
{
  "$schema": "https://json.schemastore.org/claude-code-settings.json",
  "permissions": {
    "allow": ["Bash(npm run lint)", "Bash(npm run test *)"],
    "deny": ["Read(./.env)", "Read(./.env.*)", "Bash(git push *)"]
  }
}
```

**Detalles de la sintaxis:** `Bash(git log *)` permite `git log` con cualquier argumento (el `*` va después del subcomando). En rutas, `/` al principio se ancla a la raíz del proyecto: `Edit(/docs/**)`.

*Verificado contra la documentación oficial (code.claude.com/docs, Settings y Permissions) el 19/11/2026.*
