## Concepto

**Qué problema resuelve.** El proyecto de hoy se configura distinto, aunque las ideas sean las mismas: inyección generada en compilación, JSON a objetos y scripts de build. Esta lección te da el mapa para que un `build.gradle.kts` con `ksp(...)` y `@HiltViewModel` no te tome por sorpresa.

**Antes vs. ahora.**

- `@Component` + `inject(this)` en cada Activity → `@HiltAndroidApp`, `@AndroidEntryPoint` y `@HiltViewModel`. Se mantiene que Dagger genera el grafo en compilación.
- `@SerializedName` + Gson por reflexión → `@Serializable`, con un plugin del compilador. Se mantiene el DTO separado del modelo de dominio.
- `build.gradle` en Groovy y versiones sueltas → `build.gradle.kts` + `gradle/libs.versions.toml`.
- `kapt` → `ksp`: el procesador sigue generando código, pero sin los stubs de Java.

Son tres cambios con la misma lógica: **pasar errores de ejecución a compilación** y **dejar de escribir código repetitivo**.

## Ejemplo

```kotlin
// build.gradle.kts del módulo app
plugins {
    alias(libs.plugins.ksp)
    alias(libs.plugins.hilt)
    alias(libs.plugins.kotlin.serialization)
}
dependencies {
    implementation(libs.hilt.android)
    ksp(libs.hilt.compiler)
}
```

```kotlin
@Serializable
data class TareaDto(val id: Long, val titulo: String, val completa: Boolean = false)

@HiltViewModel
class TareasViewModel @Inject constructor(
    private val repo: TareasRepository,
) : ViewModel()
```

Si el JSON no trae `completa`, Kotlinx usa el `false` por defecto. Si no trae `titulo`, que no tiene valor por defecto, falla **al parsear**, con un error claro, y no después con un `NullPointerException` en la UI.

*Los nombres de los alias (`libs.plugins.hilt`, etc.) dependen de cómo estén declarados en tu `libs.versions.toml`.*
