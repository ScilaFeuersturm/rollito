## Concepto

**Qué problema resuelve.** Llegás con un modelo mental de vistas que se mutan y de Java con `null` por todos lados. Esta lección conecta cada pieza vieja con la nueva, para que el código de Compose no parezca magia.

**Antes vs. ahora.**

- `findViewById` + `textView.setText(...)` → una función `@Composable` que recibe datos y los dibuja.
- `RecyclerView` + `Adapter` + `ViewHolder` + `DiffUtil` → `LazyColumn` con `key`.
- Un POJO con getters, `equals` y `hashCode` a mano → una `data class`.
- `if (tarea != null)` en cada lugar → el tipo dice si puede faltar (`String?`) y el compilador te obliga a decidir.

En Compose, la UI es una función del estado: **UI = f(estado)**. No guardás referencias a vistas ni las actualizás. Cambiás el estado y Compose vuelve a ejecutar (recompone) lo que lo lee. `LazyColumn` compone solo lo visible, como el reciclado de antes, y la `key` le da identidad a cada ítem.

## Ejemplo

```kotlin
data class Tarea(val id: Long, val titulo: String, val nota: String? = null)

@Composable
fun ListaDeTareas(tareas: List<Tarea>, onClick: (Long) -> Unit) {
    LazyColumn {
        items(tareas, key = { it.id }) { tarea ->
            Text(
                text = tarea.titulo,
                modifier = Modifier
                    .clickable { onClick(tarea.id) }
                    .padding(16.dp),
            )
        }
    }
}
```

La función no sabe de dónde vienen las tareas ni qué pasa al tocarlas: recibe datos y avisa con un callback. Es lo mismo que hacías con la vista pasiva de MVP, pero sin interfaz `View`.

*El código usa Compose, así que no se compila en `android-samples`. Probalo en Android Studio con la tarea de abajo.*
