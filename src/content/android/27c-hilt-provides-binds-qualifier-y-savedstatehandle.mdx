## Concepto

**Qué problema resuelve.** Hilt necesita saber cómo crear cada cosa que se pide. Hay tres formas de decírselo, y una herramienta para cuando hay dos cosas del mismo tipo.

- **`@Inject constructor`:** para tus clases. Hilt mira el constructor y resuelve los parámetros.
- **`@Binds`:** "cuando pidan esta interfaz, usá esta implementación". Va en un módulo abstracto, sin cuerpo.
- **`@Provides`:** "así se construye". Para clases de librerías o que se arman con código.
- **`@Qualifier`:** distingue dos bindings del mismo tipo. Sin qualifier, Dagger falla con `DuplicateBindings`.
- **`@HiltViewModel`:** el ViewModel recibe dependencias por constructor y se obtiene con `hiltViewModel()`.
- **`SavedStateHandle`:** Hilt lo provee solo en `ViewModelComponent`. Trae los argumentos de navegación y guarda estado que sobrevive a la muerte del proceso.

**Antes vs. ahora.** En Dagger "a mano" escribías un `@Provides` para casi todo. Hoy la regla es: `@Inject constructor` por defecto, `@Binds` para interfaces, y `@Provides` solo cuando no queda otra.

## Ejemplo

Un qualifier para un segundo `OkHttpClient` (verificado compilando con Hilt 2.60.1):

```kotlin
@Qualifier
@Retention(AnnotationRetention.BINARY)
annotation class ConAuth

@Module
@InstallIn(SingletonComponent::class)
object ClientesModule {
    @Provides @Singleton @ConAuth
    fun clienteConAuth(base: OkHttpClient): OkHttpClient = base.newBuilder()
        .addInterceptor { chain ->
            chain.proceed(chain.request().newBuilder().header("Authorization", "Bearer TOKEN").build())
        }
        .build()
}

class PerfilApi @Inject constructor(@ConAuth private val cliente: OkHttpClient)
```

`newBuilder()` reutiliza el pool de conexiones del cliente base. `@Binds` y `SavedStateHandle` están en el proyecto de live coding (`di/Modulos.kt` y `DetalleViewModel`).
